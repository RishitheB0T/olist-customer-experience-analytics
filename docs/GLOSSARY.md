# Glossary

Plain meanings of every new term in this project. Codex quizzes me from this file.

Format: **Term** — plain meaning — tiny example

## Phase 0 — Setup

- **.gitkeep** — an empty file that keeps an empty folder in Git (Git ignores empty folders) — `sql/.gitkeep` makes `sql/` appear on GitHub
- **PATH** — the list of folders Windows searches when you type a command — `psql` fails if its folder isn't on PATH
- **pip** — the tool that downloads and installs Python packages — `pip install pandas`
- **package** — ready-made code someone else wrote that you can install and reuse — pandas is a package for working with tables
- **service** — a program Windows keeps running in the background — PostgreSQL runs as the service `postgresql-x64-18`
- **.gitignore** — a list of files and folders Git must never track or upload — `data/` in it keeps the CSVs off GitHub
- **environment variable** — a setting stored outside the code that a program reads at run time — `PGPASSWORD=...`
- **.env file** — a private file holding environment variables like passwords; never uploaded — `.env` holds my real database password
- **placeholder** — a fake value showing what goes in a spot — `your_password_here` in `.env.example`
- **virtual environment** — a private Python setup for one project, so its packages don't clash with others — the `.venv/` folder
- **Git** — a tool that saves snapshots of your project so you can go back in time — `git commit` saves one snapshot
- **repository (repo)** — a project folder that Git tracks, with its full history — `olist-customer-experience-analytics`
- **commit** — one saved snapshot of the project, with a short message — `chore(setup): add folders...`
- **push** — upload your new commits to GitHub — `git push origin main`
- **remote / origin** — the copy of the repo on GitHub; `origin` is its nickname — `origin` = github.com/RishitheB0T/...
- **branch / main** — a line of history; `main` is the main one — we commit everything to `main`
- **line endings (LF/CRLF)** — the invisible "new line" mark; Windows and Linux use different ones, Git converts them — harmless warning during `git add`
- **activate (a virtual environment)** — switch your terminal to use the project's private Python — `.\.venv\Scripts\Activate.ps1` adds `(.venv)` to the prompt
- **interpreter** — the program that reads and runs Python code — `.venv\Scripts\python.exe`
- **execution policy** — a Windows rule about which PowerShell scripts may run — `RemoteSigned` lets local scripts run
- **requirements.txt** — the shopping list of Python packages a project needs — `pandas==3.1.0`
- **pinning (a version)** — fixing an exact version so everyone installs the same thing — `==3.1.0` instead of just `pandas`
- **driver** — the small piece of code that lets a program speak one database's language — `psycopg2` for PostgreSQL
- **import** — loading a package into your Python code so you can use it (like Java's `import`) — `import pandas`
- **dependency** — a package that another package needs to work, installed automatically — jupyter pulls in IPython
- **database** — an organised store of tables that many programs can read and write — our `olist` database in PostgreSQL
- **engine (SQLAlchemy)** — Python's reusable "phone line" to a database — `create_engine(url)`
- **connection URL** — one line holding where the database is and how to log in — `postgresql+psycopg2://user:***@localhost:5432/olist`
- **transaction** — a group of database changes that all succeed or all get cancelled — like a bank transfer: debit and credit together
- **autocommit** — every command is saved immediately, with no transaction around it — needed for `CREATE DATABASE`
- **idempotent** — safe to run again; a second run changes nothing — `create_database.py` says "already exists"
- **Kaggle** — Google's free website for sharing datasets, notebooks and data competitions — where the Olist data lives
- **CLI (command-line interface)** — a tool you control by typing commands instead of clicking — `kaggle datasets files ...`
- **authentication** — proving to a service who you are — `kaggle auth login` in the browser
- **access token** — a secret "digital key" a tool uses instead of your password; never share or commit it — stored in `C:\Users\<me>\.kaggle\`
- **dataset slug** — a dataset's short ID on Kaggle: owner/name — `olistbr/brazilian-ecommerce`
- **CSV file** — a plain-text table: one row per line, values separated by commas — `order_id,customer_id,...`
- **row / column** — a row is one record (one order); a column is one field (e.g. order date) — orders has 99,441 rows and 8 columns
- **shape** — a table's size as (rows, columns) — `df.shape` gives `(99441, 8)` for orders
- **DataFrame** — pandas' name for a table of data in Python — `df = pd.read_csv(path)`
- **licence (CC BY-NC-SA 4.0)** — the rules for using the data: credit the source, no commercial use, share alike — written in our README
- **unzip** — unpack a compressed .zip file into normal files — `--unzip` in the Kaggle download

## Phase 1 — Business question

- **business question** — the one question the whole analysis must answer for a real decision — "what is linked with unhappy customers?"
- **stakeholder** — the person or team who will use your results to decide something — Olist's customer experience team
- **problem brief** — a short document that pins down the question, what to check and how to measure it — `docs/problem_brief.md`
- **working definition** — a first, provisional meaning we may refine later — "unhappy" = 1 or 2 stars
- **pattern (to check)** — a question about two things that might go together; not proof that one causes the other — "is late delivery linked with low scores?"
- **comparing like with like** — comparing groups that are the same in an important way, so another difference doesn't mislead you — only on-time orders when checking product categories
- **80/20 (Pareto) check** — testing whether a small share of items accounts for most of a result — do 20% of sellers get most bad reviews?
- **repeat purchase** — a customer coming back to order again — the same `customer_unique_id` on two orders
- **carrier** — the delivery company that moves the parcel from seller to customer — `order_delivered_carrier_date` is the hand-over
- **baseline** — the starting picture everything else is compared with — total orders, statuses and review coverage before any filtering
- **attribution** — deciding which thing a result belongs to — which seller an order's review is about
- **count vs rate** — how many times something happens vs how often, relative to size — 50 bad reviews out of 5,000 orders (1%) vs 10 out of 20 (50%)
- **follow-up window** — a fixed period after an event in which you watch what happens next — every customer gets the same window after their review
- **anchor (date)** — the moment a time window starts counting from — follow-up starts at `review_answer_timestamp`
- **date vs timestamp** — a date is just the day; a timestamp also has the time of day — `2018-01-18` vs `2018-01-18 21:46:59`
- **verify, don't assume** — check a rule in the data every time instead of trusting it holds — test "one deadline per order" in the pipeline
- **KPI (key performance indicator)** — one of the few numbers a team watches to judge how things are going — unhappy order rate
- **main KPI (north star)** — the single most important KPI that everything else supports — unhappy order rate in this project
- **numerator / denominator** — the top and bottom of a fraction: "how many" out of "how many" — 1-2 star orders ÷ reviewed orders
- **mean vs median** — mean = add up and divide; median = the middle value once sorted, not pulled by extreme values — waits of 2, 3, 40 days: mean 15, median 3
- **breakdown (slice)** — the same KPI split by a group — unhappy rate by product category
- **scope** — what the analysis covers and what it deliberately leaves out — competitor prices are out of scope
- **limitation** — an honest weakness in the data or method that limits what you can conclude — only customers who answered the survey are seen
- **exclusion table** — a step-by-step count of which rows each filter removed and why — 99,441 orders → only delivered → only reviewed → ...
- **unit of analysis** — what one row stands for in a given analysis — one order, one seller or one customer
- **non-response (self-selection)** — the people who answer a survey may differ from those who don't — happy customers may skip the survey
- **eligible orders** — the orders that have everything a measurement needs — delivered orders with both a delivery date and a promised date
- **subset** — a smaller group taken from a bigger one — reviewed orders are a subset of delivered orders

## Phase 2 — Clean data

- **function** — a named, reusable block of code that takes inputs and returns a result (like a Java method) — `get_engine("postgres")`
- **module** — one Python file whose functions other files can import — `src/db.py` is the module `src.db`
- **Python package (folder)** — a folder of modules, marked by `__init__.py` — `src/`
- **python -m** — run a module by its dotted name from the project root, so `from src.db import ...` works — `python -m src.create_database`
- **refactor** — change how code is organised without changing what it does — moving connection code into `src/db.py`
- **DRY (don't repeat yourself)** — keep each piece of logic in one place so a fix happens once — one `get_engine()` for every script
- **layer (raw / clean / analytics)** — stages the data passes through, each one more trustworthy and ready to use — raw = untouched copy of the CSVs
- **schema (in a database)** — a named folder of tables inside one database — `raw.orders` is the table `orders` in the schema `raw`
- **data type** — what kind of value a column holds: text, number, date... — raw layer: every column is `text`
- **NULL** — the database's "no value here" mark; not zero and not empty text — an order with no review comment
- **BOM** — an invisible mark some programs put at the start of a text file; it can sneak into the first column name — `﻿product_category_name`
- **`if __name__ == "__main__":`** — "run this only when the file is run directly, not when imported" (like Java's `main`) — bottom of `load_raw.py`
- **chunk (chunksize)** — sending data in batches instead of all at once — 10,000 rows per batch to PostgreSQL
- **fail fast** — stop at the first sign of a problem instead of carrying on with bad data — `load_raw.py` stops if a row count doesn't match
- **exit code** — the number a program returns when it finishes: 0 = success, anything else = error — `SystemExit("Stopping: ...")` gives exit code 1
- **config (settings file)** — one file holding shared settings that many scripts use — `src/config.py` lists the 9 required files
- **GROUP BY** — sort rows into piles by a column, then count or sum each pile — orders per `order_status`
- **window function (OVER)** — a calculation that looks across many rows without merging them — `sum(count(*)) OVER ()` = total of all piles, for a percentage
- **LEFT JOIN** — join two tables but keep every row from the left one, even with no match — orders with no review still appear (0 reviews)
- **CTE (WITH ...)** — a named mini-query you can use like a table in the next step — `WITH per_order AS (...)`
- **NOT EXISTS** — keep a row only if a matching row does NOT exist in another table — orders that have no items
- **cast (::)** — convert a value from one type to another — `'2017-10-02 10:56:33'::timestamp`
- **date_trunc** — cut a date-time down to the start of its month/day/year — `date_trunc('month', ...)` gives 2017-10-01
- **profiling** — measuring raw data (counts, blanks, duplicates, odd values) before trusting it — `sql/profile_values.sql`
- **primary key** — the column whose value is different in every row, so it identifies the row — `order_id` in `orders`
- **composite key** — a key made of two or more columns together — `order_id + order_item_id` in `order_items`
- **broken link (orphan row)** — a row pointing at an ID that doesn't exist in the other table — a product category with no English translation
- **UNION ALL** — stack the results of several queries on top of each other — one table with a row per check
- **FILTER (WHERE ...)** — count only the rows that match a condition, inside one query — `count(*) FILTER (WHERE price::numeric <= 0)`
- **CASE WHEN** — SQL's if/else, giving a value per row — `CASE WHEN gap < 1 THEN 'under 1 day' ... END`
- **CREATE TABLE ... AS SELECT** — build a new table from a query's result — `CREATE TABLE clean.orders AS SELECT ...`
- **constraint** — a rule the database itself enforces, refusing data that breaks it — `PRIMARY KEY (order_id)` rejects duplicate orders
- **foreign key** — a constraint saying "this column must match an ID in another table" — every `clean.orders.customer_id` must exist in `clean.customers`
- **flag (boolean column)** — a true/false column marking rows with a problem, instead of deleting them — `flag_handover_before_purchase`
- **coalesce** — use the first value that isn't NULL — `coalesce(check, false)`: a check on a missing date counts as false
- **rollback** — undo everything a transaction did, as if it never happened — a failed build leaves no half-made tables
- **NOT NULL** — a constraint saying a column can never be empty — `clean.orders.customer_id` must always be filled in (a foreign key alone lets NULL through)
- **numeric(12, 2)** — an exact decimal number type: up to 12 digits, 2 after the point (no rounding errors, unlike float) — prices like `58.90`
- **alias (AS)** — a new name for a column in a query's result — `product_name_lenght AS product_name_length` fixes a misspelling
- **build order** — tables that point at others must be built after them — orders before order_items; products and sellers before order_items
- **CASCADE (in DROP)** — also remove things that depend on what you drop, such as foreign keys pointing at it — `DROP TABLE clean.products CASCADE`
- **PARTITION BY** — splits rows into groups for a window function, without merging them — `row_number() OVER (PARTITION BY order_id ...)` numbers reviews 1, 2, 3 inside each order
- **row_number()** — gives each row in a group a position 1, 2, 3... in a chosen order — sort by score, keep row 1 = the lowest score
- **tie-breaker** — a second (and third) sort rule for rows that are equal on the first — two 1-star reviews: take the latest answer
- **deterministic** — gives the same answer every time it runs — adding `review_id` as the last tie-breaker makes the choice deterministic
- **CHECK constraint** — a rule the database tests on every row; rows that break it are rejected — `CHECK (review_score BETWEEN 1 AND 5)` rejects a 6
- **partial unique index** — "no duplicates" applied only to rows that match a condition — one `is_order_review = true` per order; other reviews are free
- **percentile_cont(0.5)** — the PostgreSQL way to get the median — `percentile_cont(0.5) WITHIN GROUP (ORDER BY days)`
- **sensitivity check** — re-running a result with a different reasonable rule to see how much it changes — lowest vs latest review: 137 vs 98 unhappy orders
- **zip code prefix** — the first 5 digits of a Brazilian postcode; covers a small area, not one house — `01310` is part of São Paulo
- **latitude / longitude (lat / lng)** — a map position: north-south and east-west, in degrees — São Paulo is about lat -23.5, lng -46.6
- **bounding box** — a rough rectangle on the map used to catch impossible points — a lat of 45 is far outside Brazil's box
- **exact duplicate** — a row that is a perfect copy of another; it adds no new information — the same prefix and point listed 10 times
- **outlier** — a value far away from the rest, often an error — one point 2,000 km from all the others in its prefix
- **robust (statistic)** — barely moved by a few outliers — the median is robust, the average is not
- **star schema** — one central fact table linked to several dimension tables, like a star — `fact_order` in the middle, customer / seller / product / date around it
- **fact table** — one row per event, holding the numbers you add up or average — one row per order with delivery days and review score
- **dimension table** — describes the who, what, where or when of a fact — `dim_customer` holds each customer's city, state and map point
- **grain** — what exactly one row of a table stands for — `dim_customer`: one row per customer_id (= one per order)
- **date table** — one row per calendar day with handy columns (month, weekday...) — Power BI uses it for monthly trends
- **generate_series** — PostgreSQL function that makes a list of values, e.g. every day between two dates — `generate_series('2016-01-01', '2018-12-31', interval '1 day')`
- **temporary table (ON COMMIT DROP)** — a scratch table that disappears when the build's transaction ends — `order_item_summary` holds one row per order just long enough to build `fact_order`
- **join fan-out** — a join that copies rows because one side has several matches — joining orders to raw items gives one row per item, so summarise items per order first
- **haversine formula** — the standard way to get the straight-line distance between two map points on the round Earth — São Paulo to Rio is about 360 km
- **calendar days** — count of date changes, ignoring the time of day — 24 Nov 15:30 → 2 Dec 09:10 = 8 calendar days (not 7 days 17 hours)
- **nullif(x, 0)** — gives NULL when x is 0, otherwise x; avoids a "division by zero" crash — `freight / nullif(price, 0)`
- **IS DISTINCT FROM** — "not equal", but NULL vs NULL counts as equal (like `Objects.equals` in Java) — `NULL IS DISTINCT FROM NULL` is false
- **bool_or** — true if at least one row in the group is true — `bool_or(handover_late)` = "was any item of this order late?"
- **header / detail tables** — one table for the whole thing, one for its lines — `fact_order` (the receipt) and `fact_order_item` (each line on it)
- **data quality test** — a query that counts rows breaking a rule; 0 = PASS — `SELECT count(*) AS bad_rows FROM fact_order WHERE delivery_days < 0`
- **regression test** — checks that numbers recorded earlier haven't changed by accident — "reviewed orders must still be 98,673"
- **correlated subquery** — a subquery that re-runs once for every outer row (can be very slow) — `min(score)` per review took minutes; a GROUP BY + join took under a second
- **pipeline** — a fixed series of steps that turns raw data into finished tables, run with one command — `python -m src.pipeline`: load raw → clean → analytics → tests
- **command-line flag** — an extra word after a command that changes what it does — `--skip-raw` skips the slow raw load
- **sys.argv** — the list of words typed after `python` when a script starts (like `String[] args` in Java's `main`) — `"--skip-raw" in sys.argv`
- **fail fast** — stop at the first error instead of carrying on with broken data — the pipeline stops if a build or test fails
- **atomic (all-or-nothing)** — a group of changes that either all happen or none do — the 8 SQL builds run in one transaction; one failure undoes all of them
- **reproducible** — anyone can rerun the saved code and get the same numbers — every number in the data quality report comes from a saved .sql file
- **data quality report** — a document listing each problem found in the data, how many rows have it, and the rule used — `docs/data_quality_report.md`
- **.gitattributes** — a file telling Git how to treat files, e.g. which line endings to keep — `* text=auto eol=lf`
- **mermaid** — a text format that GitHub draws as a diagram — the pipeline flowchart in README.md

## Phase 3

- **denominator** — the "out of how many" in a rate — unhappy rate = 14,533 unhappy ÷ 98,673 reviewed orders
- **rate vs share** — rate = how common something is inside a group; share = how much of the total a group holds — not-delivered orders: unhappy rate 78.21%, share of all unhappy orders 15.29%
- **band (bucket)** — a range that groups many values into a few labels — days late: on time, 1-3, 4-7, 8+
- **on-time delivery rate** — delivered on or before the promised day ÷ delivered orders with both dates — 93.23% (P1)
- **mixed-up groups (confounding)** — two groups differ in more than one way, so you can't tell which difference goes with the result — late orders surveyed before delivery were also much later (median 9 vs 2 days)
- **delivery stage** — one part of the journey: seller (purchase → hand-over to carrier) or carrier (hand-over → customer) — median 2 + 7 days (P2)
- **route** — where a parcel goes from and to, here seller state → customer state — `SP -> RJ`
- **single-product order** — an order whose items are all the same product, so its review can be tied to one category and listing — 95,430 of 98,666 orders with items
- **ntile(4) / quarter** — splits sorted rows into 4 equal-sized groups — price quarter 1 = cheapest quarter of its category, 4 = most expensive
- **thin listing** — a product page with little information (few photos, short description) — an indirect clue, not a quality measure
- **concentration** — how much of a total sits with a few members; compare it with their share of orders, not just the total — top 20% of sellers: 84.80% of unhappy reviews but also 80.04% of orders
- **minimum group size** — the smallest group allowed to get its own rate, so tiny groups don't give noisy numbers — 50 reviewed orders per seller (provisional, set in Phase 4)
- **repeat purchase rate** — customers who order again within a fixed window ÷ customers with that full window — 180 days: 1.33% unhappy vs 1.80% others
- **full window** — the whole follow-up period fits before the data ends, so "didn't come back" is real, not just unseen — 53,522 customers for 180 days
- **data end (effective)** — the last day the data is complete enough to trust — 2018-08-31 (almost no orders after it)
- **90th percentile (p90)** — the value 90% of rows are below — item fee share p90 = 0.64: 9 in 10 items have a fee under 64% of the price
- **matplotlib** — Python's standard library for drawing charts — `plt.subplots(3, 1, sharex=True)` = 3 panels sharing one time axis
- **small multiples** — several small charts with the same axis instead of one crowded chart (or two y-scales) — orders, on-time rate and unhappy rate in 3 panels
- **histogram** — bars counting how many values fall in each range — days to delivery, 1 bar per day
- **long tail** — a few very large values far from the rest that pull the average up — delivery: median 10 days, mean 12.5, longest 210
- **regex match (~)** — "does this text contain this pattern?" — `msg ~ 'quebrad'` matches quebrado / quebrada (broken); `n[aã]o` matches nao and não
- **unpivot (CROSS JOIN LATERAL VALUES)** — turns several yes/no columns into one row per column, so one GROUP BY covers them all — 7 themes become 7 rows
- **keyword check (rough)** — counting texts that contain chosen words; misses some, catches some wrong ones — 'not received' in 29.90% of unhappy comments
- **spot check** — reading a few real examples to see whether a rule catches the right thing — 2 comments per theme
- **DuckDB** — a small SQL database that runs inside Python and reads CSV files directly, no server needed — `read_csv('olist_orders_dataset.csv')` in the Kaggle notebook
- **in-memory database** — a database kept only in the computer's memory; it disappears when the program stops — `duckdb.connect()` with no file name
- **QUALIFY** — a filter on a window function's result, like WHERE but applied after the window is worked out — `QUALIFY row_number() OVER (...) = 1` keeps one review per order
- **kernel-metadata.json** — the settings file Kaggle reads when you push a notebook: ID, title, file, dataset, public or private — `"dataset_sources": ["olistbr/brazilian-ecommerce"]`
- **kaggle kernels push** — uploads a notebook to Kaggle and runs it there ("kernel" = Kaggle's word for a notebook) — `kaggle kernels push -p kaggle/k1_unhappy_customers`
- **403 Forbidden** — a website's answer meaning "I know who you are, but you're not allowed to do this" — Kaggle's reply to our first push

## Phase 4
- **SciPy** — Python's standard library for statistics (tests, intervals) — `stats.binomtest(14533, 98673)`
- **sample** — the data we happen to have, out of everything that could have happened — our 98,673 reviewed orders
- **standard error** — the typical wobble of a rate from one sample to another; smaller for bigger groups — √(p × (1 − p) ÷ n)
- **95% confidence interval** — a range the true value probably lies in; 95% of ranges built this way contain it — unhappy rate 14.73%, interval 14.51-14.95%
- **Wilson interval** — a confidence interval for a rate that stays accurate for small groups and rates near 0% or 100% — 23 of 76 orders: 21.09-41.33%
